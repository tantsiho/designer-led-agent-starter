# 14 DOCS MAINTENANCE

這份文件定義文件分層與長期維護方式。

規範文件不是開工前一次寫完就不動。它會在開發過程中持續被補強。每次實作、稽核、上線檢查、風險檢查或設計者補充，都可能讓真源文件變得更完整。

## 文件分層

| 類型 | 用途 | 例子 | 規則 |
|---|---|---|---|
| 現行真源 | 後續代理必須遵守 | PRODUCT_TRUTH, RULES, FLOWS | 優先讀 |
| 工作中草稿 | 尚未定稿 | PM_QUESTIONS | 不可當硬規則 |
| 歷史參考 | 了解脈絡 | old notes | 不可優先於現行真源 |
| 封存 | 已過時 | archive | 只查證，不作新預設 |
| Runbook | 操作與驗證 | deployment, smoke | 按環境使用 |

## 回寫規則

以下情況必須更新文件：

- 設計者補充或修正產品真相
- 實作時發現規則矛盾
- 能力被改成關閉中或未來工程
- 架構決策改變
- 本地與上線環境差異被發現
- 新風險或 abuse case 被發現
- 測試或 smoke 發現流程缺口

## 開發中規範產生

如果代理在實作中發現以下情況，不應只修 code，也應補文件：

- 原本沒定義的角色或權限
- 原本沒定義的狀態轉移
- 原本沒定義的錯誤處理
- 原本沒定義的資料保存位置
- 原本沒定義的環境差異
- 原本沒定義的 abuse case
- 原本沒定義的驗收條件
- 原本沒定義的「現在不做」或「未來再做」

原則：

> 每一次踩坑，都要變成下一輪代理不用再踩的規範。

## 封存規則

文件過時時，不要直接刪除。應：

1. 標註已封存
2. 寫明為何封存
3. 指向新的真源文件
4. 避免後續代理誤用
